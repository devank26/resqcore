2. Operating Systems Concepts Applied in ResQCore

2.1 Priority Preemptive Scheduling (Disaster Triage Engine)

In operating systems CPU scheduling, tasks are assigned a priority value. When a higher-priority task arrives, the scheduler immediately preempts (suspends) lower-priority execution to allocate CPU quanta to the critical process.

Application in ResQCore:

ResQCore adopts the internationally standardized START / SALT Triage Protocol mapped directly into an OS Preemptive Priority Queue:

Triage Level OS Priority Equiv. Clinical / Disaster Criteria Scheduler Preemption Behavior
Red (Immediate) Priority 0 (Highest) Severe hemorrhage, trapped underwater, respiratory arrest Immediate Preemption: Automatically interrupts non-critical missions; alerts nearest fleet unit with sirens.
Yellow (Delayed) Priority 1 (High) Fractures, severe injuries but airway stable Dispatched sequentially behind Level 0; queue aging prevents starvation.
Green (Minor) Priority 2 (Normal) Walking wounded, dry shelter requests, food packets Standard FIFO queue when tactical response units are idle.
Black (Deceased) Priority 3 (Lowest) No pulse, catastrophic fatal trauma Mortuary recovery batch processing during post-incident stabilization.
Starvation Prevention via Task Aging

To avoid starvation of Level 2 (Green) logistical missions during continuous Level 0 alerts, the scheduler applies an Aging Function: $P_{\text{effective}} = P_{\text{base}} - \alpha \cdot \Delta t$. If a non-urgent request remains unserved for over 4 hours, its priority escalates automatically.

2.2 The Producer-Consumer Problem & Bounded Buffers

When a cloudburst strikes, tens of thousands of citizens tap the emergency button simultaneously. If the database processed each request synchronously, database connection pools would deplete within milliseconds, crashing the platform.

ResQCore Solution:

  • Producers: Distributed Flutter Citizen Mobile App clients generating SOS events.
  • Bounded Buffer: In-memory Redis Stream and Node.js bounded FIFO queue with maximum threshold $M = 50,000$ messages.
  • Consumers: Multi-threaded dispatch workers and automated geolocation assignment engines.
  • Backpressure Semaphores: If the buffer approaches 90% capacity, non-critical telemetry messages (e.g. general battery reports) are dropped with counting semaphores, ensuring 100% buffer allocation for life-threatening SOS packets.

2.3 Concurrency Control & Mutual Exclusion (Double-Assignment Prevention)

In a command room with 15 operators monitoring tactical maps, a race condition can occur if Operator A and Operator B attempt to assign Rescue Helicopter Falcon 01 to two distinct incidents at the exact same millisecond.

Implementation: Two-Tier Mutual Exclusion

  1. Database Row-Level Exclusive Lock: 
    -- Critical Section protected via pessimistic row-level locking
BEGIN TRANSACTION;
SELECT id, callsign, status 
FROM rescue_teams 
WHERE id = 'heli-falcon-01' AND status = 'ready' 
FOR UPDATE; -- Acquires Mutex Lock on this specific row

UPDATE rescue_teams 
SET status = 'dispatched', active_incident_id = 'RQ-261014-9921' 
WHERE id = 'heli-falcon-01';
COMMIT;
  2. Distributed Mutex (Redis Redlock): When multiple Node.js instances balance load, an atomic distributed lock SET lock:unit:falcon_01 token NX PX 4000 ensures mutual exclusion across different physical servers.

2.4 Deadlock Avoidance: Banker's Algorithm in Disaster Logistics

Disaster zones suffer from acute scarcity across multiple distinct resource types: Rescue Boats ($R_1$), Alpine Helicopters ($R_2$), Paramedic Squads ($R_3$), and Oxygen Concentrators ($R_4$).

The Deadlock Condition:

If Mission $\alpha$ acquires 2 Boats and holds them while waiting for 1 Paramedic squad, and Mission $\beta$ acquires the Paramedic squad and holds it waiting for 2 Boats, the system enters Circular Wait, deadlocking both missions.

The ResQCore Banker's Algorithm Rule:

Before granting any resource reservation, the dispatch algorithm verifies whether allocating the vector leaves the remaining resources in a Safe State:

Vector Definition: Available: [Boats: 3, Helicopters: 1, Paramedics: 4, Oxygen: 6] Allocation Matrix: Current assignments per active mission Max Demand Matrix: Declared incident maximum requirement Need Matrix = Max - Allocation Safety Test: Find an index i such that: Need[i] <= Available If found: Available = Available + Allocation[i] Repeat until all missions finish. If no such sequence exists, the request is REJECTED or DELAYED.

Furthermore, circular wait is fundamentally eliminated by enforcing Strict Hierarchical Resource Ordering: Resources must be claimed in the order: $\text{Transport} \to \text{Medical Personnel} \to \text{Equipment}$.

2.5 Memory Management, Virtual Memory & Caching (LRU / TTL)

High-frequency GPS tracking streams 20 updates per second across rescue fleets. Attempting to write every raw ping to relational disk storage causes severe disk I/O thrashing.

  • Time-To-Live (TTL) Caching in Redis: Active telemetry pings are written to in-memory Redis hashes with a 60-second sliding expiration TTL. The latest known location is immediately readable in $O(1)$ time, while persistent PostgreSQL storage stores aggregated historical checkpoints every 30 seconds.
  • Least Recently Used (LRU) Map Tile Cache (Mobile): The mobile client limits offline satellite tiles to a strict 150 MB boundary. When new topography is downloaded, an LRU Eviction Policy purges the least-recently viewed sectors.

2.6 Asynchronous I/O & Event Multiplexing (epoll / IOCP)

Traditional thread-per-connection architectures (like classical Apache HTTP) require 1MB of stack memory per client. Managing 15,000 citizens in a crisis would demand 15 GB of RAM merely for thread overhead, causing severe context-switching churn.

ResQCore leverages Node.js and libuv, using OS-level I/O Multiplexing (epoll on Linux, IOCP on Windows). A single thread monitors thousands of network file descriptors, waking up only when packet data arrives. This delivers sub-millisecond dispatch responsiveness with less than 120 MB of total memory consumption.

2.7 Android Process Lifecycle & Foreground Services

Mobile OS kernels utilize the Low Memory Killer (LMK) to terminate background apps when RAM is needed. If a rescuer navigates rugged terrain with the screen off, standard background location tasks would be killed within 5 minutes.

The ResQCore Rescue Teams App binds its location engine to an Android Foreground Service tied to an active, persistent status bar notification. This sets the process oom_adj score to FOREGROUND_APP (0), guaranteeing the OS kernel never terminates GPS telemetry during active search and rescue operations.

3. Computer Science Algorithms & Data Structures

3.1 Spatial R-Tree Indexing (PostGIS GIST)

Searching geographic entities via linear coordinate comparisons requires $O(N)$ comparisons. Over 100,000 registered citizens, evaluating distances sequentially takes seconds.

ResQCore builds Generalized Search Trees (GIST) based on the R-Tree Algorithm. Geographic coordinates are grouped hierarchically into Minimum Bounding Boxes (MBR):

[ Root MBR: Uttarakhand State ] / \ [ Region Alpha: Chamoli ] [ Region Beta: Dehradun ] / \ / \ [ Sector 4-A ] [ Sector 4-B ] [ Ward 12 ] [ Ward 14 ] / \ / \ / \ / \ P1 P2 P3 P4 P5 P6 P7 P8

Any bounding box search descends the tree by testing intersection against bounding rectangles, reducing the query complexity to $O(\log N)$ and executing in under 2 milliseconds.

3.2 K-Nearest Neighbors (k-NN) Spatial Search

When a citizen activates an emergency SOS, the platform computes the 3 nearest available response units. Rather than scanning all teams, PostGIS executes a Priority-Queue-driven k-NN Search using the bounding box distance operator (<->): 

-- Sub-2ms k-NN Spatial Search using R-Tree Index
SELECT 
    callsign,
    unit_type,
    ROUND(ST_Distance(current_location::geography, ST_Point(78.0322, 30.3165)::geography)::numeric, 0) AS distance_meters
FROM rescue_teams
WHERE status = 'ready'
ORDER BY current_location <-> ST_SetSRID(ST_Point(78.0322, 30.3165), 4326)
LIMIT 3;

3.3 Computational Geometry: Ray-Casting Algorithm

To issue automated evacuation alerts when flood barriers breach, the system evaluates which citizens are located inside an irregular flood hazard polygon. This utilizes the Ray-Casting Algorithm (Jordan Curve Theorem):

Point Inside Polygon (Odd Intersections = 3) Point Outside Polygon (Even Intersections = 2) ┌──────────────────────┐ ┌──────────────────────┐ │ P (Inside) │ │ │ │ *══════╦═════════╪══════► [Ray] │ │ │ ║ │ │ │ *══════╦═══════╦════► [Ray] └────────────╫─────────┘ └──────────────────────┘ 1 2 ║ (EVEN = OUTSIDE) (ODD = INSIDE)

A horizontal ray is cast from the citizen's coordinate to infinity. The number of polygon edge intersections is counted:

  • If the intersection count is ODD, the citizen is located INSIDE the hazard zone $\to$ Immediate Evacuation Siren.
  • If the intersection count is EVEN, the citizen is located OUTSIDE the zone $\to$ Advisory notification only.

3.4 Graph Theory: Dijkstra / A* with Dynamic Edge Penalties

Standard road routing algorithms calculate shortest distance or travel time based on normal speed limits. In a disaster, following standard shortest paths leads ambulances into submerged bridges or active mudslides.

ResQCore implements A* (A-Star) Pathfinding on the road network graph $G = (V, E)$, with dynamic edge cost functions: $$C(e) = \text{Length}(e) \cdot \left[1 + W_{\text{water}} \cdot \text{Depth} + W_{\text{debris}} \cdot \text{Severity} + W_{\text{grade}} \cdot \text{Slope}\right]$$ If a road is flagged as Completely Inundated or Bridge Collapsed, the edge weight is set to $\infty$, completely pruning it from the exploration priority queue and routing convoys along safe mountain ridges.

3.5 Flow Control: Token Bucket & Debouncing

  • Input Debouncing (Flutter Client): In [welcome_screen.dart](file:///c:/resqcore-disaster%20mangment%20platform/citizen%20app/lib/screens/welcome_screen.dart), _lookupAccount() delays execution for 300ms after the last keystroke, preventing database connection thrashing during typing.
  • Token Bucket Rate Limiting (Server Gateway): Each IP / User bucket refills at 10 tokens/minute with burst capacity of 15. Prevents denial-of-service and panic button hammering from flooding the message broker.

4. Academic Defense & Viva Q&A Cheatsheet

Q1: How does your platform prevent double-dispatch of the same rescue boat?
Answer: We enforce Mutual Exclusion through a two-tier mechanism: pessimistic row-level database locking (SELECT ... FOR UPDATE) within a single database transaction, paired with distributed mutexes via Redis Redlock across multi-node API gateways.
Q2: Why did you choose PostGIS R-Trees instead of calculating distance in JavaScript/Dart?
Answer: Calculating distances in application memory requires an $O(N)$ full scan, which degrades catastrophically at scale. PostGIS uses R-Trees (GIST index) to hierarchically subdivide geography into Minimum Bounding Boxes, evaluating nearest neighbors in $O(\log N)$ logarithmic time under 2ms.
Q3: What OS scheduling algorithm is modeled in your emergency triage system?
Answer: Priority Preemptive Scheduling. Incidents follow the START triage standard (Red = Immediate, Yellow = Delayed, Green = Minor). Red incidents immediately preempt active lower-priority missions. Task Aging ($P_{\text{eff}} = P - \alpha t$) is implemented to prevent starvation of logistical tasks.
Q4: How does your architecture handle cellular network blackouts?
Answer: We implement an Offline-First 3-Tier model: Tier 1 saves encrypted reports to local SQLite outbox on device; Tier 2 utilizes a Store-and-Forward retry worker upon signal recovery; Tier 3 leverages peer-to-peer BLE and Wi-Fi Direct mesh for device-to-device rescuer sync without internet.
Q5: How is the Producer-Consumer problem manifested in your SOS pipeline?
Answer: Citizens act as concurrent producers emitting emergency packets into a bounded Redis queue. Dispatcher services act as consumers. Bounded buffers and counting semaphores regulate backpressure, ensuring database connection pools are never exhausted.
