Project Abstract 
(Brief restatement of your project’s main goal. Max 300 words). 
ResQCore is a disaster-response platform for handling emergency requests when rescue teams, ambulances and supplies 
are limited. The main idea of the project is to treat every emergency request like an OS process, so that the most critical 
case gets resources first instead of the first-come-first-served order. The OS side covers scheduling, safe resource 
allocation, synchronization and deadlock detection, and the DBMS side keeps the data consistent with transactions, 
constraints and audit logs. 
In Phase 2 we completed the mobile application layer of the project. We built two Android apps in Flutter and a command 
centre. The first is the ResQCore citizen app, where a person can report a flood, earthquake, fire or other emergency in a 
few steps, share location, track the request, see hazard zones and live rescue teams, read safety guides and call 112. The 
second is the RescueTeam Ops app for rescue teams and operators, which has a dashboard, incident list, live tactical map, 
team and member tracking, shelters with casualty triage, team chat and an SOS screen. 
Both apps are built and packaged as release APKs, and the command centre is also built. At present they run on sample 
data stored inside the app. The next phase is to build the OS simulation engine and the database, and connect the apps to 
them. 
 
Updated Project Approach and Architecture 
(Describe your current approach, including system design, communication protocols, libraries used, etc. Max 300 words). 
 
Current approach: we first designed all the screens in Stitch (an AI UI design tool), saved the designs as screen images and 
HTML, and then converted them into Flutter code. We kept the front-end separate from the backend so that the OS and 
DBMS parts can be connected later without redesigning the screens. 
• Language and framework: Dart with Flutter (Material design), targeting Android. 
• State management: the citizen app uses the Provider package (RescueProvider with ChangeNotifier); the team app 
uses its own AppState class with ChangeNotifier. 
• Structure: each app is split into models, screens, widgets and theme folders. Models include incident, rescue team, 
shelter, evacuee, hazard zone, safety guide and chat message. 
• Maps: the live map is drawn with Flutter CustomPaint (tactical map canvas and radar widget), not with an online map 
service. 
• Other libraries: google_fonts and intl in the citizen app. The Android manifest asks for location, call and camera 
permissions (internet and location in the team app). 
• Data: all incidents, teams, shelters and alerts are sample data inside the code for now. 
Planned system design: the apps will talk to a backend over REST APIs (JSON over HTTP). The backend will have the OS 
simulation engine (PCB, schedulers, Banker's algorithm, mutex/semaphore, RAG deadlock detection) and a relational 
database as the permanent store, connected through an integration layer.

Challenges/Roadblocks 
(Describe the challenges that you have faced or are facing so far and how you plan to solve them. Max 300 words). 
• All data is sample data. The apps do not use a real database or server yet, so a request sent from the citizen app does 
not reach the team app. We plan to build the backend and APIs in the next phase and replace the sample data step by 
step. 
• OS and DBMS parts are not built yet. The scheduling algorithms, Banker's algorithm, deadlock detection and the 
database design are still on paper. This is the biggest gap. We will start with the database schema and the scheduler, 
since the other parts depend on them. 
• Two separate apps. The citizen app and the team app have their own models and themes, and some code is 
repeated. We will keep common models in one shared format (through the API) so that both apps stay in sync. 
• Map and GPS are simulated. The map is drawn with CustomPaint and locations are fixed values. We will test a real 
location and map package after the backend is ready. 
• Testing is very limited. Only the default smoke test exists in each app. We plan to add unit tests for the OS algorithms 
and widget tests for the main screens. 
• App size and team coordination. The APKs are about 54 MB because of the large scenario images, so we will 
compress them. We also need a shared GitHub repository and regular commits so that all four members can work on 
the same code.

Project Outcome/Deliverables 
(Describe what are the key outcomes / deliverables of the project. Max 200 words). 
 
By the end of the project we will deliver: 
• A working citizen app, a rescue-team app for Android (already built as APKs) and a command centre. 
• An OS simulation engine that treats each emergency request as a process and supports the scheduling algorithms, 
Banker's algorithm, synchronization and deadlock detection. 
• A relational database with 13 tables, constraints, indexes, views, stored procedures, triggers, transactions and 
recovery. 
• An integration layer and APIs that connect the apps, the OS engine and the database. 
• Performance reports (waiting time, turnaround time, response time, throughput and resource utilization) and a full 
disaster scenario demo. 
 
Progress Overview 
(Summarize how much of the project is done, what's behind schedule, what's ahead of schedule. Max 200 words.) 
The front-end part is complete. Both apps and the command centre are built, packaged as release APKs and all main 
screens work with sample data. We think about 35% of the full project is done. 
Ahead of schedule: the user interface of both apps. The designs were finished early, so the screens are ready to connect 
to the backend. 
Behind schedule: the OS simulation engine, the database and the integration between them. Code for these parts has not 
been written yet, and they are the core of the project. Testing is also behind. 
For the next phase we will start with the database schema and the scheduler, then connect the apps through APIs.
